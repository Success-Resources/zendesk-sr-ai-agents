Phase 1: a Zendesk ticket becomes an internal note

The customer never sees this reply yet. A person still sends the real email. The assistant only writes a draft inside the ticket, as an internal note.

What “done” looks like for Phase 1. A ticket is created in Zendesk. A few seconds later, an internal note appears on that same ticket. The note is a draft answer, written from the GitHub knowledge base. Staff can copy or edit it, then send it themselves.

How one ticket moves, in words

  1. A customer emails. Zendesk creates a ticket.
  2. Your existing tags still apply (MMI, QL, refund, and so on).
  3. A new trigger fires: “this ticket was created, send it to our Python address.”
  4. Python checks the request is really from Zendesk, then queues the work so Zendesk does not time out.
  5. Python looks at the tags and picks Maya, Quinn or Rafa. If it cannot tell, it writes a short internal note: “needs a person.”
  6. Python reads that assistant’s responses.jsonl from GitHub.
  7. An AI model writes a draft using only those answers. It is told not to invent prices or approve refunds.
  8. Python posts that draft on the ticket as an internal note. The customer does not see it.
  9. A person opens the ticket, reads the note, and sends the real reply.

Build this, step by step

Do these in order. Today: only Step 1 and Step 2. Do not skip to the AI model until Zendesk can already talk to Python.

Order
  1. Zendesk: your account + API token — you can do this now, using your own login.
  2. Vercel + Python service — a free public HTTPS URL (Hobby plan).
  3. Webhook + trigger (after the URL exists).
  4. Python posts a fake internal note (still no AI).
  5. Load GitHub knowledge.
  6. Route Maya / Quinn / Rafa by tags.
  7. Turn on the AI draft.
  8. Three Views for reviewers.
1

Zendesk: use your own account, then create an API token

Yes — use your personal Zendesk account for Phase 1. You do not need a new “AI Assistant” user, and you do not need a new email, to get the first connection working. When the Python service posts an internal note, that note will appear as you (your name in Zendesk). That is fine while you are testing. A dedicated “AI Assistant” user is optional later, so staff can see which notes came from the machine. Open the later section at the bottom of this step if you want that.

What an API token is

It is a long password that lets a program talk to Zendesk as you. The program will use:

  • Your Zendesk login email
  • The word /token after that email
  • The API token instead of your real password

Example (never put a real token in GitHub):

Username: you@successresources.com/token
Password:  the-long-token-you-copied-once

Zendesk tokens are account-wide. They are not “owned” by one person. The email you put in the program is what decides whose name appears on the internal note. For now, that email is yours.

You must be an administrator

Only an admin can turn on token access and create a token.

  1. Log into Zendesk as you normally do.
  2. Look for the four-square Zendesk Products icon (top of the screen) and open Admin Center. If you cannot see Admin Center, you are an agent only. Ask an admin to either make you an admin, or to do the token steps below and send you the token privately.

Find your subdomain (you will need this in Python)

Look at the browser address bar while you are in Zendesk. It looks like:

https://YOURSUBDOMAIN.zendesk.com/...

The part before .zendesk.com is the subdomain. Write it down. Example: if the URL is https://successresources.zendesk.com, the subdomain is successresources.

Turn on API token access

Tokens are off until an admin switches them on.

  1. In Admin Center, open Apps and integrations.
  2. Open APIs → API configuration.
  3. Tick Allow API token access.
  4. Click Save.

If this page is missing, you are not an admin, or the account cannot use API tokens (see the date warning below).

Create the token

  1. Still in Admin Center, open Apps and integrations → APIs → API tokens.
  2. Click Add API token.
  3. Description: SR Phase 1 internal notes — Vercel (any clear name is fine).
  4. Click Save. Zendesk shows the full token once.
  5. Copy it immediately into a password manager (or a notepad you will not email). You will never see the full token again after you close the window.
  6. Click Save again to leave the screen.
Do not put this token in GitHub, in Slack, or in this project folder. Treat it like a password. If you ever paste it into a chat or a screenshot, deactivate that token in the same API tokens list and make a new one.

Store these three values

NameWhat to save
SubdomainThe part before .zendesk.com
EmailThe email you use to log into Zendesk (your personal account)
API tokenThe long string you copied once

Prove the token works (on your Windows PC, before any hosting)

Open PowerShell. Paste this, then replace the three values in quotes. Press Enter.

$sub   = "YOURSUBDOMAIN"
$email = "you@your-email.com"
$token = "PASTE_THE_TOKEN_HERE"

$pair = "${email}/token:${token}"
$b64  = [Convert]::ToBase64String([Text.Encoding]::ASCII.GetBytes($pair))
Invoke-RestMethod -Uri "https://$sub.zendesk.com/api/v2/users/me.json" -Headers @{ Authorization = "Basic $b64" }

If it worked, PowerShell prints your Zendesk user, including your name and email. Step 1 is done.

If you get 401 or “Couldn’t authenticate you”:

  • API token access is still off, or
  • The email is not exactly your Zendesk login email, or
  • A space was copied with the token, or
  • You are not an agent/admin on that account.
Date warning (Zendesk is retiring API tokens). New API tokens can still be created on existing accounts until 27 October 2026. After that, Zendesk wants OAuth instead. All API tokens stop working on 30 April 2027. Create this token now, keep using it for Phase 1, and plan to switch the Python service to OAuth later. If Add API token is missing, your account may already be blocked from new tokens — say so and we will set up OAuth instead.
Step 1 is complete when: you have subdomain + your email + a token, and the PowerShell test printed your Zendesk user.
Later (not now): add a user called AI Assistant

Only do this when you want internal notes to show a machine name instead of your name. You still do not need a special “AI email inbox”.

  • Zendesk needs a unique email that is not already used by you or anyone else on the account. You cannot reuse your own login email.
  • A real mailbox is best, for example ai-assistant@yourcompany.com, so you can accept the Zendesk invite. A plus-alias such as you+ai@gmail.com sometimes works if Zendesk accepts it.
  • The user must be an Agent (or Admin), not an end-user. End-users cannot post internal notes. A Light Agent is often too limited for the API.
  • Adding an Agent usually costs an extra paid seat. That is why Phase 1 uses your account.
  • After the user exists, you only change the Python ZENDESK_EMAIL to that user’s email. You can keep the same API token.
  • Then, in the trigger (Step 3), ignore comments from that user so the bot cannot loop.

Until then: skip this. Your personal account is the correct Phase 1 setup.

Put a tiny Python service on Vercel (free Hobby plan)

No Hostinger VPS. No extra monthly server bill for Phase 1. Vercel Hobby is free. It gives you HTTPS and a public URL such as https://zendesk-sr-ai-agents.vercel.app. Your affordablecloudsecurity.com website stays where it is. Do not add this API into the existing workshop Vercel project — create a new project.

Vercel does not keep a server switched on. When Zendesk (or you) call the URL, Vercel starts the Python app, it answers, then it sleeps. That is enough for Phase 1.

2a. The Python program (already in this project)

The starter lives at github/sr-ai-agents/service/. For Step 2 it only does two things:

  • GET /health → returns {"ok": true, "phase": 1} so you can test in a browser.
  • POST /zendesk/webhook → accepts JSON, writes a log line, replies {"received": true}. No AI yet. No Zendesk note yet.

That folder is already on your personal GitHub (rayriakram/success-resources). Vercel Hobby will deploy from there. The company repo can keep a copy of the same files; Vercel just cannot import that private org repo on the free plan.

Why Deploy is greyed out. Vercel Hobby cannot deploy from a private repo inside a GitHub organisation. Success-Resources/zendesk-sr-ai-agents is exactly that, so the Deploy button stays disabled (sometimes with a “upgrade to Pro” message). Your workshop site worked because it was not this private org repo. For Phase 1, import the Python app from your personal GitHub instead. The company repo can stay the knowledge home. You can point Vercel at the org later if you pay for Pro.

2b. Create a new Vercel project (not the workshop site)

  1. If you already started an import of Success-Resources/zendesk-sr-ai-agents, cancel it. Go back to the Vercel dashboard.
  2. Open vercel.com/new and log in with GitHub.
  3. Import the personal repo rayriakram/success-resources (your GitHub, not the Success-Resources org). Search for success-resources if the list is long.
  4. On the configure screen, click Root Directory → Edit and set it to: 
    github/sr-ai-agents/service
    That folder is where app.py lives in the personal repo. If you set only service, Vercel will not find the app and Deploy can stay disabled.
  5. Framework should show FastAPI or Other. Leave Build Command and Output empty.
  6. Skip environment variables for this first deploy (see 2c). An empty variable row also greys out Deploy.
  7. Click Deploy.

  2. Open the deployment. Copy the Production URL. It looks like: 
    https://zendesk-sr-ai-agents.vercel.app
    Yours may include a random word. That URL is what Zendesk will call later. Write it down.

2e. Test from your browser

Open (use your real Vercel URL):

https://YOUR-PROJECT.vercel.app/health

You should see {"ok":true,"phase":1}.

Then, from PowerShell on your PC:

Invoke-RestMethod -Method POST `
  -Uri "https://YOUR-PROJECT.vercel.app/zendesk/webhook" `
  -ContentType "application/json" `
  -Body '{"id": 1, "subject": "test"}'

You should see received: True.

To see the log line: Vercel → this project → Logs (or the deployment → Functions). You should see webhook received ticket_id=1.

Step 2 is complete when: /health works in the browser over https, and the POST test returns received. Zendesk is not connected yet. That is Step 3. Stop here until both tests work.
If something fails
  • Deploy button grey / “upgrade to Pro” → you imported the private org repo. Cancel and import rayriakram/success-resources instead.
  • Deploy still grey after switching repo → Root Directory must be github/sr-ai-agents/service, and there must be no empty Environment Variable row.
  • Build cannot find FastAPI / app → Root Directory is wrong. Fix it in Project Settings → General → Root Directory, then Redeploy.
  • /health is 404 → you opened the workshop project URL by mistake, or Root Directory is wrong.
  • You added env vars after the first deploy → they often do not apply until you Redeploy the production deployment.

3

Connect Zendesk to that URL

Do this only after Step 2’s /health page works. Admin Center → Apps and integrations → Webhooks → create a webhook pointing at https://YOUR-PROJECT.vercel.app/zendesk/webhook. Turn on signing (HMAC). Copy the signing secret into the Vercel project: Settings → Environment Variables → ZENDESK_WEBHOOK_SECRET. Then Redeploy so the new secret is loaded.

Then create a trigger:

  • When: Ticket is created (not “updated” — that avoids loops while notes come from your own user)
  • Then: Notify webhook, send the ticket id, subject, description, tags, requester name

Test: create a dummy ticket. In Vercel → this project → Logs, you should see a POST. If you do not, stop here and fix the webhook before adding any AI.

4

Python posts a fake internal note

When a ticket arrives, Python calls Zendesk with the token from Step 1:

  • URL like https://YOURSUBDOMAIN.zendesk.com/api/v2/tickets/{id}.json
  • Add a comment with public: false
  • Text can be: “Phase 1 test. The service received this ticket.”

Open the ticket as an agent. You should see a private note in your name. The customer should see nothing new. When this works, the pipes are correct. The AI is not involved yet.

5

Load the knowledge from GitHub

The Python service downloads Success-Resources/zendesk-sr-ai-agents (zip of main) on startup and about every 10 minutes. It reads the email answers under knowledge-hub/ (maya.md, quinn.md, rafa.md). If GitHub is down, it uses the bundled copy next to app.py.

GitHub is the source of answers. The internal note is that email text, so staff can send the same words to the customer. Open /health and check source is github:Success-Resources/zendesk-sr-ai-agents@main.

If the repo is private, set Vercel env GITHUB_TOKEN (a GitHub personal access token with repo read) and Redeploy.

7

Turn on the AI draft

Only after steps 1 to 6 work. The service then:

  1. Takes the customer’s message.
  2. Finds the closest questions in that assistant’s file.
  3. Sends those answers plus the customer message to an AI model (any provider, behind one function in your code).
  4. Tells the model: use only this knowledge, do not invent prices, do not approve refunds, write a draft for staff.
  5. Posts the result as an internal note (in your name for now, or as AI Assistant later).

Add a tag such as ai_draft_only so you can make a View of tickets that already have a draft.

They open the ticket, read the internal note, and send the public reply themselves. No extra buttons.

Safety for Phase 1

  • Every comment the service posts must have public: false.
  • The first trigger must be “Ticket is created”, so your own internal notes cannot loop.
  • One internal note per ticket in this phase. Do not keep rewriting the same ticket.
  • If the model is unsure, the note should say so, and a person answers.

What this phase is not

The assistant does not email the customer. It does not close the ticket. It does not approve money. Those come later, and only for Maya and Quinn on simple questions, after the drafts are consistently good.
